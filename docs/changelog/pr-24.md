# Stop Pi checkpoints doubling and remove what a finished run leaves behind

## Summary

Every Pi checkpoint was stored twice in the `pi-workspaces` bucket: once as
1 MB upload pieces under `transfer/`, once as the final `<digest>.json`.
Neither copy was ever deleted, and every older checkpoint of a run was kept
although only the newest is read. On production that was 17.9 MB of a 23.5 MB
bucket. Live event rows in `pi_run_events` also stayed after the answer was
published.

This PR deletes staged pieces once their bytes are stored, keeps only the
newest checkpoint of a run, and clears live rows and leftover transfers when
an answer is published. No new service and no schema change. It is the first
of three PRs from the approved storage review; R2 and Durable Object work
follow separately.

## Changes

**Transfers** (`src/lib/astro/pi-transfer.ts`, broker route)
- `removePiTransfer` deletes a transfer's manifest and pieces. Called after
  `blob/commit` and `checkpoint/commit` succeed. Best effort: it logs and
  never fails the commit.
- `removePiRunTransfers` sweeps everything under a run's `transfer/`,
  covering restore copies and abandoned uploads.

**Checkpoints** (`src/lib/astro/pi-store.ts`)
- `prunePiCheckpoints` runs after `worker_save_pi_checkpoint` accepts a new
  receipt: removes older archives, then their receipt rows. It never removes
  the object the kept receipt names (identical bytes share one address).
- `clearPiRunEvents` deletes a run's live rows.

**Publication** (`src/lib/astro/pi-publish.ts`)
- New optional `clearScratch` dependency, run after the publication RPC and
  proposal queueing. A failure is logged; the published answer stands.

**Operator script** (`scripts/cleanup-pi-storage.mjs`)
- Dry-run by default; `--apply` removes pre-existing leftovers for runs that
  are not active. On staging it also trims `cron.job_run_details` and
  schedules a daily trim. Resolves the project host through a public
  resolver because some networks return a wrong address for `*.supabase.co`.

## Testing

- `src/lib/astro/pi-retention.test.ts` (6 tests): newest checkpoint kept,
  other runs untouched, shared-digest object kept, transfer removal, run
  sweep leaves checkpoints and blobs, event clearing scoped to the run.
- `pi-publish.test.ts`: scratch cleared after `finish`; a failing cleanup
  still returns `complete`.
- `scripts/cleanup-pi-storage.test.mjs` (2 tests), added to
  `test:release-preflight`.
- `npm test`, `npm run typecheck`, `npm run lint` pass locally.
- Script applied on staging: bucket 195 objects / 6.8 MB to 12 objects /
  0.38 MB; cron log 17,599 rows to 1,441. Production: dry run only.

## Risk / rollback

- A retried `checkpoint/commit` after a lost response now finds its pieces
  gone. The runner re-uploads pieces before every commit, and the receipt
  RPC already treats the same sequence and digest as done.
- A reader holding an older receipt while a newer one is committed could see
  a missing archive. Restore runs at runner start and publication after the
  final checkpoint, so they do not overlap checkpoint writes of the same run.
- Revert the commit to restore the old behaviour; deleted leftovers are not
  needed by any reader.

## Review focus

- That nothing reads a non-latest checkpoint: `readPiCheckpoint`,
  `readPiRecovery`, the prior-session restore in `pi-runtime.ts`.
