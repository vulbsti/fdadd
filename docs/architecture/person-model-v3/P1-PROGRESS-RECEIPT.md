## P1 exit decision and P2 handoff

1. Begin P2 with one person identity/revision authority, the `astro_profiles.id` compatibility adapter, trusted write boundaries, typed job payloads, atomic publication, and correction/exclusion invalidation. Do not start P5 screen parity on session-local summaries.
2. Retain `aidoraa-staging`, the branch-only Preview variables, and the staging scheduler as the integration target. Every hosted test must keep the fail-closed host/ref guards and use an exact disposable-user teardown receipt.
3. Track three bounded reliability follow-ups without reopening P1: server-controlled `Last-Event-ID` assertion if exact offset replay becomes mandatory; clearer affordance for internally scrollable message/reading panes in P5; and cleanup of existing PL/pgSQL unused-variable/text-to-UUID-array lint warnings during P2 schema work.
4. Carry the pure-computation recompute boundary into P2 worker authority. Cache uniqueness gives one durable Atros result, but exactly-once physical Sandbox execution across a process crash requires a stronger external-effect receipt protocol.

Architecture assessment: this is not a narrow request-only patch. The transactional outbox, service-only store contract, Workflow self-fence, typed verifier/Atros results, canonical question identity, preserved resume trigger, deployed sweeper, and fail-closed staging harness are reusable by the P2 job/revision authority. P1 is accepted because contract, automated, fault, provider/Sandbox, deployed recovery, reload, and responsive visual evidence now agree. It still does not create the v3 person revision authority, publication fencing, astrology-off guarantee, exactly-once external calculation execution, or approved life-map UI; those remain later phase gates, not implied parity.
